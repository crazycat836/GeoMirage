GeoMirage — 連線狀態流程圖 給第一次看這個專案的人 · 2026-05-19

本文件先解釋 GeoMirage 是什麼、為什麼需要追蹤「連線狀態」， 再介紹後端如何維護它、各種情境下會發生什麼事，最後給想看程式碼的人一條建議路徑。

這專案是？ 詞彙速查 使用者視角 三種狀態 後端架構 七個情境 背景任務 讀程式碼 已知斷點

1. 這個專案在做什麼？

TL;DR

GeoMirage 是一個 macOS 桌面應用 (Electron + FastAPI)，可以連到 iPhone 並「假裝」它的 GPS 位置 —— 開發者可以在不動到實體裝置的情況下，測試 App 在不同地點的行為。

  • iPhone 可以透過 USB 或 Wi-Fi tunnel 與電腦連線
  • 後端會透過 Apple 內部 protocol (DVT) 注入 GPS 座標
  • 前端 (Electron) 需要即時知道：「裝置現在連上了嗎？訊號還在嗎？」 ← 這就是「連線狀態」

為什麼「連線狀態」這麼重要？因為 iPhone 透過 Wi-Fi 連線時很容易斷 —— 螢幕鎖了、網路抖動、使用者走到別的房間，都會讓背後的 DVT channel 掉線。 使用者不會接受 App 沒反應，所以後端必須：

  • 能在約 3 秒內感知到「USB 線拔了」（每秒查一次，連續 3 次看不到才算）
  • 能在 5 秒內感知到「Wi-Fi 不通了」
  • 遇到暫時性掉線時，能自動嘗試重連（而不是直接告訴使用者「裝置已斷線」）
  • 把這些變化即時推送到前端 UI

2. 詞彙速查（會在後面反覆出現）

UDID
iPhone 的唯一識別碼。一個 40 字元字串。後端用 UDID 區分多台裝置。
usbmux
Apple 的 USB 多工服務，列出所有透過 USB 連上的 iPhone。後端每秒 poll 它一次來偵測插拔。
Wi-Fi tunnel
透過區網建立的 iPhone ↔ Mac 連線，比 USB 不穩定，但行動性高。
RSD (Remote Service Discovery)
iOS 17+ 之後 Apple 用的服務發現協定，Wi-Fi tunnel 跑在 RSD 之上。
DVT (Developer Disk Image)
Apple 內部的開發者通道。GeoMirage 透過 DVT 注入 GPS 座標。一旦這個 channel 掉了，就無法注入位置。
SSoT (Single Source of Truth)
單一狀態來源。本專案的 SSoT 就是 connection_state.py，所有想知道「裝置現在到底是不是連著」的程式，都得問它。
WebSocket (WS)
前端與後端之間的長連線，用來即時推送狀態變化（連上、斷線、不穩定）。
Watchdog / Liveness loop
背景一直跑的監控任務。USB watchdog 每秒查一次裝置列表；liveness loop 每 5 秒 ping 一次 Wi-Fi tunnel。

4. 後端怎麼描述「連線狀態」？三種狀態

狀態白話意思UI 顯示能下 GPS 指令嗎？
DISCONNECTED 沒連 / 連線已失敗 灰色「未連線」 ❌ 不行
CONNECTED 連線正常 綠色「已連線」 ✅ 可以
DEGRADED 連線抖了一下，正在嘗試恢復 琥珀色「重連中」（MiniStatusBar 的裝置 pill 變色並閃爍，裝置清單該列狀態顯示「重連中」） ⚠️ 暫時不行（會 retry）

為什麼需要 DEGRADED 這個中間狀態？

iPhone 透過 Wi-Fi 連線時，DVT channel 偶爾會掉（例如 iPhone 螢幕鎖了 2 秒）。 如果我們一掉就標記成 DISCONNECTED，使用者就會看到「斷線」的紅色錯誤訊息 —— 可是 1 秒後它可能又恢復了，這樣 UX 會閃爍得很難看。

所以加一個 DEGRADED：表示「我們知道有問題，正在自動重連，請稍等」。 重連成功 → 回到 CONNECTED；重連失敗 → 才真正進入 DISCONNECTED。

為什麼要設計成 SSoT？

重構前，「裝置現在是不是連著」這個資訊散落在 4 個地方：DeviceManager 的內部字典、 TunnelRunner 的旗標、各個 location service 的快取、前端的 WS state。 結果就是常常彼此不一致 —— UI 顯示已連線，但實際下 GPS 指令會失敗。

把狀態統一到 ConnectionStateStore 之後，所有變化都要透過它的 API，順帶觸發 WS 廣播：

  • connect_device / disconnect_device：連線或斷線，同時改 transport 與狀態。
  • teardown_device：固定順序拆掉一台裝置 —— 先停 GPS 引擎（terminate_engine），再斷 transport，最後轉成 DISCONNECTED。引擎停止失敗也不會跳過斷線。
  • announce_connected：transport 已經由呼叫端建好（Wi-Fi tunnel 走 dm.connect_wifi_tunnel），只更新狀態並廣播 device_connected。
  • reannounce_connected：USB 拔掉後改走 Wi-Fi tunnel 時，先轉 DISCONNECTED 再轉回 CONNECTED，讓前端重畫 pill。
  • mark_degraded / mark_recovered：DVT channel 重連期間的中間狀態。

前端因此永遠跟得上後端。

6. 七個情境深入看

從這裡開始進入細節。每個情境都用同樣的結構：情境描述 → 流程圖 → 結果摘要。

情境 1：使用者把 iPhone 用 USB 線插上電腦

USER
會發生什麼： 插上線本身不會連線。前端呼叫 GET /api/device/list 時， DeviceManager.discover_devices 以 autopair=False 讀 usbmux，新裝置只會出現在清單裡， 不會配對、也不會跳出「信任這部電腦」。使用者按下連線，後端才配對並經過 SSoT 連線。 device_watchdog 刻意不處理「新裝置出現」。

結果： 插線後裝置出現在清單；只有使用者按連線，才會配對並連上。

情境 2：使用者拔掉 USB 線

AUTO
會發生什麼： USB 監控（device_watchdog）每秒問 usbmux 目前有哪些 USB 裝置，發現已連線的 UDID 不在列表了。 為了避免 usbmux 偶爾漏報，必須連續 3 次都看不到才算真的拔了（約 3 秒緩衝）。 如果這時有活著的 Wi-Fi tunnel，裝置會改走 tunnel（reconnect_usb_over_wifi），不會斷線。

情境 3：使用中 DVT channel 突然掉線（最常見的抖動）

RECOVER
會發生什麼： 使用者正在用 GeoMirage 設定假位置， 但 iPhone 螢幕鎖了 / Wi-Fi 抖了 2 秒，導致 DVT channel 斷掉。 這時 location service 會自動重連，期間狀態為 DEGRADED（UI 顯示「重連中」）。

情境 4：Wi-Fi tunnel 整條死掉（iPhone 走出 Wi-Fi 範圍）

MONITOR
會發生什麼： 不像 DVT 掉線是「上層 API 報錯」，Wi-Fi 整條死掉時可能完全沒有錯誤，只是 TCP 不通了。 所以有個 tunnel_liveness_loop 每 5 秒做兩件事： (1) 檢查 tunnel 任務本體還活著嗎， (2) TCP probe 看 RSD 連接埠通不通。

Generation guard 的小細節： 如果使用者在 probe 失敗的中途 手動停掉再重啟 tunnel（generation 編號會 +1），原本要 cleanup 的動作會被取消，避免誤殺新 tunnel。 
sequenceDiagram
    autonumber
    participant L as tunnel_liveness_loop
(每 5 秒)
    participant T as TunnelRunner
    participant SVC as wifi_tunnel_service
    participant CS as ConnectionStateStore
    participant WS as WebSocket
    participant UI as 前端 UI

    loop every 5s
        L->>T: 取得 generation + transport 狀態
        alt transport task 已死
            Note over L: 立刻判定失敗 (跳過 TCP probe)
        else
            L->>L: TCP probe RSD port
            alt 通
                Note over L: miss_count = 0 (重置)
            else 不通
                Note over L: miss_count += 1
            end
        end
    end

    Note over L: miss_count 達到 3 (約 15 秒)
    L->>T: 再次檢查 generation
    alt generation 變了 (使用者重啟過)
        Note over L: 取消 cleanup,避免誤殺
    else generation 沒變
        L->>SVC: cleanup_wifi_connections()
        loop 對每個走這條 tunnel 的裝置 (via_tunnel)
            SVC->>SVC: 關閉 GPS 引擎
            SVC->>CS: disconnect_device(udid, cause="wifi_dropped")
            CS->>WS: broadcast("device_disconnected")
            WS->>UI: 推送
        end
        L->>T: tunnel.stop()
    end
結果： Wi-Fi 真的死了之後最多 15 秒會被偵測 + 完整 cleanup，但短暫抖動不會誤殺。只清掉走 GeoMirage 自己 tunnel 的裝置（連線紀錄的 via_tunnel 為 true）；Finder「Wi-Fi 同步」的 usbmux Network 裝置有自己的 CoreDevice tunnel，不受影響。

情境 5：使用者重整 App（renderer reload）

AUTO

情境 6：API 內部偵測到狀態異常，強制重連

RECOVER
會發生什麼： 某些 API 路徑（例如 exec_with_retry） 在執行命令前，若發現底層狀態異常（找不到 engine、收到 DeviceLostError）， 會呼叫 services/engine_recovery.py 的 force_reconnect 做「先斷再連」的 hard reset，把整條鏈路打掉重練。 cause 標記為 hard_reset，前端會看到一個快速的斷-連週期。 走 GeoMirage Wi-Fi tunnel 的裝置（via_tunnel）usbmux 看不到，所以改從 tunnel 的 RSD 重新連線；tunnel 已經死了就放棄，交給 liveness loop 清理。

(先停引擎，再斷線)
    CS->>WS: broadcast("device_disconnected")
    alt 走 Wi-Fi tunnel (via_tunnel)
        H->>H: dm.connect_wifi_tunnel(tunnel RSD)
        H->>CS: announce_connected(udid, cause="hard_reset")
    else USB / usbmux
        H->>CS: connect_device(udid, cause="hard_reset")
    end
    CS->>WS: broadcast("device_connected")
    H->>H: 重建 GPS 引擎
結果： 自我修復成功時使用者只看到一閃而過的狀態切換；失敗則裝置變灰色。

7. 背景任務有哪些？為什麼需要它們？

後端啟動時會跑起幾條背景 loop，分工如下：

背景任務節奏為什麼需要它？
usbmux_presence_watchdog 每 1 秒 USB 沒有 push event，必須 poll。只偵測拔除，決定情境 2 的反應速度（插入不處理，見情境 1）。
tunnel_liveness_loop 每 5 秒 Wi-Fi tunnel 可能「靜悄悄地死掉」(無 exception)。TCP probe 是唯一可靠的偵測方式。
TunnelRunner._run 長駐 Wi-Fi tunnel 本體的傳輸 coroutine，死了的話 liveness loop 會發現。
_tunnel_watchdog one-shot 每次啟動 tunnel 時 spawn 一個（api/tunnel/lifecycle.py），專門 await tunnel task；task 崩潰時負責 cleanup。
device_health.probe_connected_devices 每次新 WS 連線 情境 5 用，防止 reload 後狀態脫節。
併發安全的設計小細節： 所有這些 loop 都跑在 同一條 FastAPI/uvicorn asyncio event loop 上， 這代表它們不會真的「同時」修改 ConnectionStateStore —— asyncio 的合作式調度保證了序列化。所以 ConnectionStateStore 內部 不需要顯式 Lock (見 connection_state.py 中 ConnectionStateStore 的 docstring)。

8. 想實際讀程式碼？建議路徑

如果你想動手改這部分，依下面的順序看可以建立最快的心智模型：

  1. backend/services/connection_state.py 整個專案的「字典 + 狀態機」核心。從 DeviceState enum、StateTransition dataclass、ConnectionStateStore 三個東西開始看。
  2. backend/main.py（特別是 lifespan / startup 段） 看清楚啟動時哪些 observer 與背景任務被裝上去：install_ws_observer()、usbmux_presence_watchdog、tunnel_liveness_loop。這裡刻意沒有啟動時自動連線。
  3. backend/services/device_watchdog.py 最簡單的 producer：只處理拔除（含改走 Wi-Fi tunnel 的 fallback）。情境 1 的連線看 backend/api/device.py 的 connect route。
  4. backend/api/websocket.py 切換到 consumer 視角。看 _send_initial_state 怎麼從 snapshot 組裝給前端；補救脫節的探測在 backend/services/device_health.py。
  5. backend/core/tunnel_liveness.py + backend/services/wifi_tunnel_service.py 搭配著看。前者偵測，後者執行 cleanup。注意 generation guard 那段。
  6. backend/services/location_service.py（_reconnect 方法） DEGRADED 狀態的整套生死。包含 DVT_RECONNECT_DELAYS 重試 schedule。
  7. backend/tests/ 的 5 個對應測試檔 test_connection_state.py、test_tunnel_liveness.py、test_websocket_initial_state.py、 test_location_service_reconnect.py、test_wifi_tunnel_service.py。它們是最好的「期望行為文件」。

9. Wi-Fi tunnel 起連與 SSoT（已修復）

POST /wifi/tunnel/start-and-connect（backend/api/tunnel/lifecycle.py）與 POST /wifi/tunnel 共用 backend/api/tunnel/_helpers.py 的 connect_device_over_tunnel：

  1. dm.connect_wifi_tunnel(rsd_address, rsd_port) 建立 transport（連線紀錄標記 via_tunnel=True）。 如果同一台已經以 USB 連著，先 connection_state.teardown_device(..., cause="replaced_by_wifi_tunnel") 停掉引擎並斷線，再連一次。
  2. connection_state.announce_connected(..., connection_type="Network", cause="wifi_tunnel") 把狀態寫進 SSoT， WS Observer 因此廣播 device_connected；從 USB 換成 Network 時也會重新廣播，前端的 pill 會更新。
  3. connection_state.create_engine_with_rollback 建立 GPS 引擎，失敗就把狀態退回 DISCONNECTED。

因此這條路徑和其他寫入者一樣經過 SSoT，§5 圖中的 P3 為實線。
